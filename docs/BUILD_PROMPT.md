# Build: Worktime — enterprise + individual time tracking

## Elevator pitch
A multi-tenant time-tracking app. Individuals log hours against projects;
managers see team hours and approve month-end timesheets; admins manage
org settings, static-data enums, and pay rates. A chat assistant can
batch-log hours and pull reports in natural language. Users can belong to
several organizations and switch between them.

## Tech stack
- **API**: NestJS (TypeScript), one controller per resource
- **DB**: Postgres. Schema owned by **Liquibase** changelogs (formatted-SQL
  style — plain SQL with `--changeset` headers, not XML/YAML — so changes
  stay readable and reviewable). Query layer: **Drizzle ORM**, with its
  `schema.ts`/`relations.ts` *generated by introspecting the database*,
  never hand-written. Liquibase and the ORM never both try to own
  migrations — pick one path and enforce it.
- **Web**: React + MUI + Vite. Left nav drawer for sections, role-gated;
  an organization switcher top-right when the user has more than one.
- **Auth**: Keycloak (SSO) as the primary IdP, same Postgres instance
  (`auth` schema), plus a local username/password + HS256-JWT fallback for
  dev parity. Every request resolves to one caller id regardless of which
  path authenticated it.
- **Email**: nodemailer, unauthenticated against a local Mailpit catcher in
  dev, switches to a real relay purely via env vars (`SMTP_USER`/`PASSWORD`
  set → auth kicks in; nothing else changes).
- **AI assistant**: OpenAI-compatible chat completions with tool-calling.
  Build it against the `openai` SDK's interface specifically *because*
  multiple providers (OpenAI, Gemini, others) expose an OpenAI-compatible
  endpoint — switching providers becomes a 3-line change (`baseURL`,
  `apiKey`, `model`), not a rewrite.
- **Infra**: Docker Compose, four environments (local/dev/vps/azure) at
  fixed port offsets. `local` runs only its dependencies (Postgres,
  Keycloak, Mailpit, a one-shot migration runner) in containers — `api`/
  `web` run natively on the host for fast reload. `dev`/`vps`/`azure`
  containerize everything, fronted by Caddy.

## Data model
- `users`, `user_identities` (provider + provider_user_id, so one user can
  have a password identity and an SSO identity)
- `organizations`, `organization_memberships` (user × org × role), so a
  user's role is **per-organization**, never a single global value
- System roles (`owner`/`admin`/`manager`/`member`/`guest`) with a
  permission matrix; org-scoped custom roles are allowed by the schema
  even if unused at first
- `organization_invitations` (email + role + token, expiring), `organization_domains`
  (auto-join by verified domain), `sso_configurations` (per-org SAML/OIDC)
- `teams`, `team_members` (with an optional assigned-manager per member —
  decide up front whether "manager" authorization means *this org's*
  managers broadly or *this member's specific* manager; don't leave the
  field unused-but-present, that's a trap for later)
- `projects`, `subprojects` (owner, type, a free-text cost-center code)
- `work_times` (user, org, project/subproject, start/end, comment)
- `static_data`: a generic `(entity, enum_name) → {key: label}` table so
  admins can edit dropdown vocabularies without a deploy. Give it a real
  unique constraint on `(entity, enum_name)` from day one — a seed script
  re-run against a table that lacks one will silently duplicate rows forever.
- `timesheet_periods`: one row per (org, user, calendar month), status
  `open → submitted → approved|rejected`. Keep this as its own table —
  never mutate or flag `work_times` rows directly. "Locked" is purely a
  lookup: does a submitted/approved period cover this entry's date?
- `member_rates`: effective-dated hourly rate per person
  (`effective_from`/`effective_to`, nullable-open-ended), for cost
  reporting without touching payroll systems
- `audit_logs`

## Features by role
- **Everyone**: log/edit/delete own time entries (blocked once their month
  is locked); daily/weekly/monthly personal overview; submit their own
  month for approval; chat assistant for their own hours/reports.
- **+ Manager**: teams and projects CRUD; per-team hours rollup by member
  with drill-down; send org invitations; approve/reject submitted
  timesheets; team-hours and project-cost report tools in the assistant.
- **+ Admin**: static-data enum CRUD; organization profile/domains/SSO;
  set pay rates (kept on a separate admin-only screen — compensation data,
  not shown to plain managers even though managers can see the resulting
  cost totals); reopen an approved timesheet period.

## Non-negotiable architectural rules
(these are the mistakes worth not repeating)

1. **Authorization is server-side, always, per request** — never rely on
   the frontend only offering valid choices (e.g. an org switcher that
   only lists the user's own orgs) as the actual security boundary.
   *Every* org-scoped endpoint must independently verify the caller is a
   member of that org (not just authenticated to *some* org) before
   returning or mutating anything. Write this as one shared helper
   (`isOrgMember`/`isOrgManagerOrAdmin`/`isOrgAdmin`) and call it from
   every handler — it's easy to add a new endpoint and forget the check,
   so audit for it explicitly, don't assume it followed from the pattern.
2. **Tool-calling AI never gets a bypass.** Each tool the assistant can
   call re-runs the exact same authorization check as its REST
   equivalent, using the caller's real identity — never the role the user
   *claims* in the chat message. Test this by literally asking the model
   to do something the user isn't allowed to, while claiming they are.
3. **Liquibase changelogs are append-only.** Never edit an applied
   changeset — add a new one. Adopting Liquibase on a database that
   already has the schema (not created via Liquibase) needs
   `changelog-sync` (marks changesets applied without re-running DDL), not
   `update`.
4. **Everything degrades gracefully, never crashes**: no `DATABASE_URL` →
   endpoints return empty/offline shapes instead of 500ing; no SMTP
   reachable → mail send is fire-and-forget, logged, never blocks the
   request; no AI provider key → a clean `{ok:false, error:'not-configured'}`,
   not an unhandled exception.
5. **Surface real errors to the user.** A form that optimistically applies
   a change locally and only silently reverts it on the next background
   refresh — with no error shown — is worse than no optimism at all. If a
   write can fail for a reason the user can act on (locked month, no
   permission), show it.
6. **File-naming conventions per framework, not one global rule**: React
   component files are PascalCase matching the component; NestJS files
   are `name.role.ts` (`.controller`, `.service`, `.guard`) — both are
   "correct," don't force one framework's convention onto the other's files.
7. **Role is resolved per-organization on every switch**, not computed
   once at login by scanning all memberships for the highest privilege —
   a manager in org A must not stay "manager" after switching to org B
   where they're only a member.

## Suggested build order
1. Schema + auth + org/membership CRUD + RBAC helpers, before any feature
   work — everything else depends on getting "who is this caller, in
   which org, with what role" right once.
2. Core time-tracking loop: log/edit/delete own entries, personal overview.
3. Teams + projects management, then team-hours rollup.
4. Invitations.
5. Static-data admin screen, org settings admin screen.
6. Timesheet lock/submit/approve — this is the point where "authorization
   per request" really gets tested, since it adds a *third* dimension
   (not just "can you see this org's data" but "is this specific month
   editable right now").
7. Cost rates + cost reporting (needs #3 and #6 done first).
8. AI assistant last — by the time you build it, every tool it needs is
   already a tested, authorized function; the assistant is just a router
   in front of things that already work correctly on their own.

## Verification standard
For each feature: unit-test pure logic (date math, permission-boundary
helpers with fake DB rows) → build clean → apply the migration to a real
throwaway Postgres and diff/verify it → curl the live API through the full
happy path *and* the denied path (wrong org, wrong role, locked period) →
drive the actual UI (Playwright or by hand) and read the screenshot, don't
just check the HTTP status. Don't call a feature done from code review alone.
